## 1. Why a chunking change is not a config edit

*Changing the embedding model underneath a live index* covered one way a corpus quietly splits in two: vectors from different models sharing an index, with no error and no way to tell which slice is which. Changing your chunking strategy breaks the same way, for a different reason. The model never has to change. The chunks themselves stop meaning the same thing.

A chunk's identity is not just its text. It's a position in a document, defined by a boundary rule - how many tokens, how much overlap with its neighbors, where the splitter is allowed to cut. That rule is baked into the chunk's ID, into "chunk 4 of document X" as a citation, into every downstream record that references a chunk by position. Change the rule for some documents and not others, and "chunk 4" stops being a stable idea. It's a different span of text depending on which rule produced it, and nothing in the index says which one that was.

| | Same chunk schema throughout | Two schemas, one index |
|---|---|---|
| "Chunk 4 of document X" | The same span, every time | A different span, depending on which schema produced it |
| Chunks per document | Predictable from the schema | Varies document to document with no visible reason |
| Overlap between neighboring chunks | Consistent | Inconsistent - some chunks share text with their neighbor, some don't |
| Failure signal | None needed | None at all - retrieval and citations are just occasionally wrong |

The last row is the trap, and it's the same trap as the model swap for the same reason: nothing throws. A query still returns five chunks. A citation still points at an ID that exists. It's only when you or a reader checks that a returned span actually contains the answer that you find out a third of your citations quietly point at half a sentence, because they were generated under a schema your current UI code assumes is still in force.

> A chunk's identity is not just its text - it's the boundary rule that produced it. Change the rule and every chunk ID means something subtly different, even though the source document never changed at all.

## 2. The migration itself

Treat a chunking change exactly like the model migration in the previous lesson: never rewrite in place, build a parallel structure, verify it, then cut over behind a pointer.

1. **Name and version the new schema.** Chunk size, overlap, and splitter choice, given an explicit name - `v2-semantic-400`, not "the new chunking." An implicit schema is one nobody can check a chunk against later.
2. **Fold the schema into every chunk's ID.** A v1 chunk and a v2 chunk of the same document must never collide, and they will unless the ID itself carries the schema name.
3. **Turn on dual writes.** Every document ingested or updated from this point gets chunked under both schemas and written to both places, exactly as a model migration dual-writes both embeddings. Skip this and anything that changes mid-migration is missing from whichever schema you finish backfilling second.
4. **Backfill by re-chunking, not re-extracting.** Walk the corpus and re-split each document under the new schema. This reads the parsed text you already kept - covered in *One corpus, three storage tiers* - not the raw source. Re-parsing a PDF you've already parsed once is the expensive mistake this migration should not also make.
5. **Verify with two different checks**, because a chunking bug can pass one and fail the other. Run your retrieval eval set (*Measuring retrieval*) for recall and ranking. Separately, spot-check a sample of returned citations by hand against the source document, confirming the span actually contains what it claims to. Recall can look fine while every citation lands one sentence early.
6. **Cut traffic over behind a pointer**, the same way a search engine's index alias handles a full reindex: the application queries "current-chunks," and current-chunks is a name you can repoint instead of a hard-coded schema version.
7. **Retire the old schema** once the new one has run against real traffic long enough to trust it, and only then.

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class ChunkSchema:
    name: str            # e.g. "v2-semantic-400", never left implicit
    max_tokens: int
    overlap_tokens: int

def chunk_id(doc_id: str, schema: ChunkSchema, ordinal: int) -> str:
    """A chunk's identity includes the schema that produced it, so a v1
    chunk 4 and a v2 chunk 4 of the same document never collide."""
    return f"{doc_id}::{schema.name}::{ordinal}"

def rechunk(doc_id: str, tokens: list[str], schema: ChunkSchema) -> list[dict]:
    """Re-split already-parsed tokens under a new schema. Takes tokens,
    not raw text - the expensive extraction step already happened once."""
    step = schema.max_tokens - schema.overlap_tokens
    chunks = []
    for i, start in enumerate(range(0, len(tokens), step)):
        window = tokens[start:start + schema.max_tokens]
        if not window:
            break
        chunks.append({
            "id": chunk_id(doc_id, schema, i),
            "schema": schema.name,
            "text": " ".join(window),
        })
    return chunks
```

Nothing here re-reads a source file. `rechunk` takes tokens that were already extracted once, which is the entire reason the parsed tier from the next lesson is worth keeping around instead of re-deriving on every migration.

## 3. Deciding whether a re-chunk is worth it

A full re-chunk costs an embedding call per chunk across the whole corpus, same as a model migration, plus the operational risk of running two schemas in parallel while you verify. That's a real bill and a real window of complexity, so the decision deserves the same discipline as deciding whether to swap embedding models - evidence first, not a hunch that smaller chunks would probably help.

| Signal | Re-chunk | Leave it |
|---|---|---|
| Your eval set shows answers split across chunk boundaries, or citations landing mid-sentence | Yes | - |
| A new chunk size or splitter wins on your own eval set by a real margin | Yes | - |
| Corpus is small enough that a full rebuild is cheap regardless | Yes, low risk either way | - |
| The gain is marginal and the corpus is large | Weigh the re-chunk cost against the gain | Often not worth it yet |

If the signal is real, run the migration exactly as above rather than toggling the config and hoping the blast radius stays small. If it isn't - if the eval set doesn't actually show a boundary problem - the fix belongs somewhere else, most often in the chunking approach's overlap setting rather than a full schema change.

Write down which chunk schema is live, since when, and what the last eval run scored against it - the same note you'd keep for a model migration, in the same place. The schema name on each chunk answers "what produced this." The note answers "why we chose it," and like the model note, it's the part that disappears first once the person who ran the migration has moved on to the next thing.

*The schema you wish you had written on day one* gave every document a `content_hash` and an `ingested_at`. This lesson is where those fields finally earn their keep - deciding how often to check a source for changes, and how to tell, cheaply, whether anything actually needs re-processing when you do.

## 1. Three ways to know something changed

There is no single right answer here, because the three mechanisms depend on what the source system is willing to give you.

| Mechanism | How it works | What it needs | Where it falls short |
|---|---|---|---|
| Polling | Periodically ask the source "what changed since my last check" | A reliable `updated_at` or similar field | Misses deletions unless designed for them; freshness is bounded by the schedule, not the change |
| Webhook | The source calls you the moment something changes | The source has to support outbound webhooks | You must be reachable and up; a missed delivery can be silently lost unless you also reconcile |
| Change-data-capture (CDC) | Read the source database's transaction log directly | Direct access to the source's log, usually your own database | Only works where you control or can attach to that log; not available against most SaaS APIs |

Polling is the default not because it is best, but because it is the only one that works against almost anything - any system with a query interface can be polled, whether or not it was built to notify anyone of changes. Webhooks are better when available, because the source tells you instead of you asking, which turns "how fresh" from a scheduling problem into a delivery problem. CDC is the most complete of the three - it reads inserts, updates and deletes straight from the log, with minimal load on the source - but it is only available where you have that level of access, which for most external SaaS sources you simply do not.

Choosing a webhook is not the end of the work, either. A webhook delivery can fail to arrive - the source retries a few times and then gives up, or your endpoint was down for the one minute it mattered. Treat a webhook as a fast path, not the only path: pair it with a slow, infrequent poll as a backstop that catches whatever the webhook missed, rather than trusting delivery to be perfect. That backstop poll can run once an hour instead of once a minute, because its job is only to catch the rare miss, not to carry the freshness target on its own.

## 2. Picking a freshness target on purpose

The 2pm policy fix should not wait until midnight, but that does not mean every document needs a webhook either. Not every document is equally urgent, and treating them all the same - one schedule for the whole corpus - is how a nightly cron job becomes the freshness guarantee for content that could not care less about it, while starving content that actually needed to be fast.

| Content | Cost of being stale | Reasonable freshness target |
|---|---|---|
| Active policy or pricing pages | High - wrong answers with real consequences | Minutes - webhook or frequent poll |
| Product documentation | Moderate - confusing but rarely harmful | Hours |
| Support ticket history | Low once resolved | Daily |
| Archived reports, old announcements | Very low | Weekly, or on demand only |

The point of a table like this is not the specific numbers - yours will differ - it is that the number should come from asking "what does it cost someone if this is wrong for X hours" rather than from whatever a cron expression already says. Set it too aggressive across the board and you pay in API load and re-embedding cost for content that never needed it. Set it too relaxed and you get exactly the 2pm-versus-midnight problem this lesson opened on.

> Freshness is a number you choose per document type, weighed against what staleness actually costs. Nightly is only correct for the documents where nobody has ever done that arithmetic.

## 3. Re-indexing only what actually changed

Once you have a mechanism for detecting change, the next mistake is re-embedding everything it points at, whether or not the content actually differs. A poll or webhook tells you a document was touched - saved, re-published, opened and closed without edits - not that its text changed. The `content_hash` from *The schema you wish you had written on day one* is what answers that second question cheaply, before anything expensive happens.

```python
import hashlib
import time

import requests

def poll_for_changes(base_url: str, api_token: str, registry: dict[str, str], since: str):
    """registry maps document_id -> last known content_hash.
    Only documents whose hash actually changed get queued for re-embedding.
    """
    headers = {"Authorization": f"Bearer {api_token}"}
    resp = requests.get(
        f"{base_url}/pages",
        headers=headers,
        params={"updated_since": since},
        timeout=30,
    )
    resp.raise_for_status()

    to_reembed = []
    for page in resp.json()["results"]:
        document_id = page["id"]
        new_hash = hashlib.sha256(page["body"].encode()).hexdigest()

        if registry.get(document_id) != new_hash:
            to_reembed.append(page)
            registry[document_id] = new_hash
        # else: the source reports a touch, but the text is unchanged - skip it

    return to_reembed, registry
```

This is the loop that makes an aggressive freshness target affordable. Polling every few minutes is cheap on the source and cheap on your pipeline as long as the expensive step - parsing, chunking, embedding - only fires on documents whose hash actually moved. Without that check, a tight polling interval just means paying full re-embedding cost on a schedule instead of paying it when something changed, and paying it far more often.

One gap this loop does not close: a deletion. A document removed from the source stops showing up in `updated_since` results entirely rather than showing up with new content, so a poll built only to catch changes will never notice it is gone. That is deliberately out of scope here - *Deleting is a feature*, later in this course, is where a removal actually gets propagated into the corpus rather than quietly forgotten.

The other habit worth building into this loop from the start is making the re-embed step idempotent. A poll that runs every few minutes will, sooner or later, be interrupted mid-batch by a deploy, a crash, or a timeout, and it will run again over some of the same documents it already processed. If writing a chunk's vector to the store is an upsert keyed on `document_id` and `chunk_index` rather than a blind insert, running the same document through twice produces the same end state instead of a duplicate row sitting next to the original. That one property is what makes an aggressive polling interval safe to leave running unattended - a mechanism that only works when every run happens to complete cleanly is not one to trust with a freshness target anyone is depending on.

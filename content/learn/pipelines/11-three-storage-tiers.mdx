## 1. Three jobs, not one blob store

It's tempting to treat "the corpus" as one thing: documents go in, chunks and vectors come out, and whatever happens in between is an implementation detail not worth persisting. That's true right up until something downstream has to change - and in a system that's alive, something downstream always eventually changes.

Split the pipeline by what actually varies independently, and three tiers fall out on their own.

| Tier | What it is | What changes it | Cost to regenerate | What breaks if lost |
|---|---|---|---|---|
| Raw | The source file, byte for byte - the PDF, the wiki export, the ticket | Never, unless the source system itself edits it | Depends on the source - sometimes trivial, sometimes gone for good | Nothing else can ever be re-derived correctly again |
| Parsed | Normalized text and structure pulled out of the raw file - *From source system to corpus* is the extraction step that produces this | A parser upgrade, a layout fix, a new extraction library | One full extraction pass over the corpus - slow, and often needs a human to catch new failure modes | Every chunking and embedding decision has to be redone from raw, at full extraction cost |
| Chunks + vectors | The retrieval-ready form: split text plus its embedding | A chunk schema change (*When the corpus itself has to move*) or an embedding model swap (*Changing the embedding model underneath a live index*) | A pass over already-parsed text - fast, mechanical, no re-extraction | Retrieval stops working, but nothing upstream is lost |

Read the middle row again, because it's the one teams skip. Parsing - turning a two-column PDF or a scanned form into clean, ordered text - is usually the slowest, most failure-prone, most manually-tuned step in the whole pipeline. It's also the one step that produces something genuinely new: text that didn't exist as a plain string before you ran extraction on it. Raw files you can always re-fetch, in principle, from wherever they came from. Chunks and vectors you can always regenerate from parsed text in minutes. Parsed text is the one thing that, once lost, costs you the whole extraction run to get back.

> The expensive step in a pipeline is the one worth storing on its own. Everything downstream of it should be cheap to redo; everything upstream of it should be cheap to re-fetch. Parsing is neither - which is exactly why it needs its own tier.

## 2. The PDF you keep re-parsing

Here's the failure this lesson opened on, made specific. A team stores raw PDFs in object storage and, once a day, runs a pipeline that parses each one, chunks the result, embeds the chunks, and writes vectors to an index. Nothing else is kept. The pipeline is a straight line from raw file to vector, with no station in between where the parsed text sits still.

Six months later, the chunking strategy needs to change - smaller chunks, real overlap, the exact migration in *When the corpus itself has to move*. That migration's whole premise is re-splitting text you already have. But there's no "text you already have" to re-split. The pipeline never wrote it anywhere; it only ever existed for the seconds it took to flow from parser to chunker in memory. So "re-chunk the corpus" quietly becomes "re-run extraction on every document in the corpus," which is a different, much slower, much more failure-prone job than the one the migration was designed to be.

This is also why the ladder in *Vector databases* - numpy array, pgvector, a dedicated store - doesn't answer the question this lesson asks. That ladder is entirely about the third tier: once you have chunks and vectors, where do you put them. It has nothing to say about whether the text underneath those vectors is kept anywhere else, because it assumes you can always get back to that text if you need to. The team above picked a perfectly good vector store off that ladder and still lost a week, because the gap wasn't in tier three. It was that tier two never existed as a tier at all.

```python
from dataclasses import dataclass
from pathlib import Path

PARSER_VERSION = "layout-aware-v3"

@dataclass
class ParsedDocument:
    doc_id: str
    parser_version: str
    text: str

def get_or_parse(doc_id: str, raw_path: Path, parsed_store: dict) -> ParsedDocument:
    """Read the parsed tier first. Only touch the raw file - the slow,
    failure-prone step - if this document hasn't been parsed by the
    current parser version yet."""
    cached = parsed_store.get(doc_id)
    if cached is not None and cached.parser_version == PARSER_VERSION:
        return cached

    text = extract_text(raw_path)          # the slow step this tier protects
    parsed = ParsedDocument(doc_id, PARSER_VERSION, text)
    parsed_store[doc_id] = parsed
    return parsed
```

`get_or_parse` is the whole idea in eight lines: check the parsed tier before you touch the raw one, and re-parse only when the parser itself has moved on. Everything downstream of this function - chunking, embedding - reads `parsed.text` and never sees a raw file at all.

## 3. What to keep, and for how long

Each tier earns a different retention policy, because each answers a different question about the corpus.

**Keep raw indefinitely, in the cheapest storage that survives.** It answers "what did the source actually say," which you need for audits, for reprocessing after a parser rewrite, and for the rare case a parsed version turns out to have silently mangled something. It doesn't need to be fast to read - a document you re-parse once every few months can live in cold, cheap object storage.

**Keep parsed text, and version it.** A parser upgrade changes what "the parsed text" means for a document, the same way a new chunk schema changes what "chunk 4" means - tag every parsed record with the parser version that produced it, for the same reason *When the corpus itself has to move* tags every chunk with its schema. Mixing text from two parser versions in one corpus, untracked, produces the identical silent split as mixing chunk schemas: some documents read one way, some another, and nothing marks which.

**Treat chunks and vectors as disposable, on purpose.** They're a fast, mechanical function of the parsed tier plus a chunking schema plus an embedding model. Once those three inputs are pinned, chunks and vectors can be deleted and rebuilt without anxiety - which is exactly the property that makes the migrations in the previous two lessons affordable to run at all. The tier worth protecting is the one they're built from.

The one habit that keeps all three tiers honest is small: whenever you write a parsed record, write the parser version next to it, and whenever you write a chunk, write the schema name next to it. Neither costs more than a string field. Both are the difference between "re-derive this in an afternoon" and "re-derive this from scratch, and hope you notice which documents still need it."

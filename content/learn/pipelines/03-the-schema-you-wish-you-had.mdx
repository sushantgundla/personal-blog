*One document, five copies* ended with a decision - pick a canonical document, mark the rest as superseded - and pointedly did not say where that mark lives. This lesson is where it lives, along with everything else a pipeline needs to know about a document before it is allowed to become a chunk.

## 1. Chunks forget where they came from unless you make them remember

Once a document is chunked and embedded, the chunk is just a vector and a string. Nothing in that vector encodes which document produced it, which version of the document that was, or when it was pulled from the source. If those facts were never captured somewhere, they are gone the instant chunking happens - there is no way to derive "which version was this?" from a chunk after the fact.

This is a different layer from *Metadata and filtering*, and it is worth being precise about the difference rather than treating the two as the same list of fields. That lesson is about query time: `tenant_id`, `allowed_group_ids`, `doc_type` sitting on the chunk row so a search can filter correctly and safely. It assumes those fields already exist and asks how to use them without a leak. This lesson is earlier and separate: deciding a document's identity, version and provenance exist at all, in a record kept independent of the vector store, before the document is ever split into chunks that get filtered.

Skip this step and the two lessons' problems compound. A corpus with no version field cannot support the recency-aware filtering the other lesson describes, because "recency" needs a trustworthy `updated_at` to filter on, and nothing manufactures that after the fact.

Play the handbook re-index forward without this registry and watch where it goes wrong. Someone starts re-chunking the employee handbook with a new chunk size. Halfway through, the job fails and gets restarted. Some chunks in the store now come from the old chunking pass, some from the new one, and both sets say `handbook.pdf` in whatever free-text field the pipeline happened to log. Nobody can write a query that says "give me only the new chunks" or "roll back to only the old ones," because nothing distinguishes them except an accident of which half of the job finished first. A `document_id` plus a `version` field would have turned that into a one-line filter. Their absence turns it into an afternoon of someone reading chunk text and guessing which pass it came from.

## 2. The fields worth having on day one

Some fields are cheap to add later. These are not - each one describes something that only exists at the moment a document arrives, and cannot be reconstructed once that moment has passed.

| Field | What it captures | Cost if missing later |
|---|---|---|
| `document_id` | A stable identity for this document, independent of any one chunk | Unrecoverable - re-derives as a "new" document every re-fetch |
| `content_hash` | A fingerprint of the document's actual text | Unrecoverable - no way to tell if content changed since last ingest |
| `source_url`, `source_system` | Where this came from, for citations and re-fetching | Unrecoverable once the source moves or is reorganised |
| `version` or `revision` | Which edition of the document this is | Unrecoverable - old and new content becomes indistinguishable |
| `ingested_at` | When the pipeline pulled it | Unrecoverable - no way to reconstruct pipeline history |
| `embedding_model` | Which model turned this chunk into a vector | Unrecoverable - a mid-migration corpus becomes unreadable |

```python
import hashlib
from dataclasses import dataclass, field
from datetime import datetime, timezone

@dataclass(frozen=True)
class DocumentRecord:
    """One row per document, decided at extraction time - not per chunk,
    and not added after the fact once the corpus already has gaps."""
    document_id: str          # stable across re-fetches of the same document
    source_system: str        # "wiki", "helpdesk", "drive"
    source_url: str
    content_hash: str
    version: str
    ingested_at: str = field(default_factory=lambda: datetime.now(timezone.utc).isoformat())

def make_document_record(source_system: str, source_id: str, source_url: str,
                          body: str, version: str) -> DocumentRecord:
    # document_id is derived from source system + source id, not regenerated
    # per fetch, so the same document always resolves to the same identity.
    document_id = hashlib.sha256(f"{source_system}:{source_id}".encode()).hexdigest()[:16]
    content_hash = hashlib.sha256(body.encode()).hexdigest()

    return DocumentRecord(
        document_id=document_id,
        source_system=source_system,
        source_url=source_url,
        content_hash=content_hash,
        version=version,
    )
```

Two design choices in that function matter more than the code itself. `document_id` is derived from the source system and the source's own ID, not generated fresh each time - so pulling the same wiki page twice always produces the same `document_id`, which is what lets deduplication and re-indexing recognise "you already have this" instead of treating every fetch as new. `content_hash`, separately, is derived from the body text, so it changes exactly when the content changes and stays fixed when it does not - that is the signal the next lesson uses to decide whether a document is worth re-embedding at all.

## 3. A registry, not just columns on the chunk table

Treat this as a document-level registry - one row per document - sitting alongside the vector store, not squeezed onto every chunk row as an afterthought. A chunk row still needs its own `parent_document_id` pointing back into this registry, and its own `chunk_index`, but the document's own identity, source, version and hash belong to the document, once, not repeated and risking drift across every chunk cut from it.

> A vector store answers "what is close to this query." A document registry answers "where did this text actually come from, and is it still current." A corpus needs both, and only one of them was designed on purpose in most pipelines.

If you are reading this with a corpus that already exists and never had a registry, the honest news is that some of it cannot be recovered - `ingested_at` for documents already ingested is gone, and `source_url` for a document whose source has since moved is a best guess at most. What you can still do is start the registry today, backfill `content_hash` and `document_id` for everything currently in the store, and accept that anything older than that point has a real gap rather than pretending a reprocessing job will quietly fix it. A registry started late is still worth more than no registry, and it is a great deal cheaper than the alternative of guessing at document history from log lines every time something goes wrong.

The payoff shows up downstream, not immediately. *One document, five copies*' canonical-versus-superseded marking is a field on this registry, not a guess reconstructed from timestamps in the vector store. *Nightly is a design choice, not a default*, next, decides whether a document needs re-fetching by comparing a freshly pulled `content_hash` against the one already in this registry - a comparison that is impossible if the registry never captured a hash in the first place. Every later lesson in this course that touches "did this change" or "which version is this" is really asking a question this registry either can or cannot answer, depending on what got decided here, before any of it seemed urgent.

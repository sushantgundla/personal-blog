## 1. What "batch complete" actually tells you

Every ingestion job in this course has, somewhere, a loop over documents and a try/except inside it. That except is there on purpose - one malformed PDF should not take down the other 9,999 documents behind it in the batch. It is also, quietly, the thing that makes "batch complete" nearly meaningless as a success signal, because catching an error and reporting overall success are two different decisions that most pipelines make with the same line of code.

| | Job crashed | Job "succeeded," items silently dropped |
|---|---|---|
| What you see | An exception, a non-zero exit code, an alert | A clean log line: "batch complete," a normal exit code |
| What actually happened | The whole batch stopped, cleanly, at a known point | Some fraction of documents never reached the index, and the loop kept going past each one |
| Who notices first | You, from the alert | A reader, from a missing search result |
| Time to diagnose | Minutes - the stack trace names the failure | However long it takes someone to notice a document isn't searchable |

The right column is the dangerous one, for the same reason a wrong-but-confident model answer is dangerous elsewhere in this course: there is no error to grep for. The job's own idea of success was never "every document landed." It was "the loop didn't crash," and those are only the same claim if you went and checked.

> A batch job's own success flag tells you the loop didn't crash. It tells you nothing about whether every document inside that loop actually reached the index - that's a separate question, and it needs a separate answer.

## 2. Three places a document silently vanishes

Once you know to look, a dropped document is one of three things, and they need different fixes.

| | Parse failure, swallowed | Dedup false positive | Write or embed failure |
|---|---|---|---|
| What went wrong | Extraction threw on this document and the per-item except ate it | The document was wrongly flagged as a near-duplicate of something else and dropped | The embedding call or the index write failed for this document, or one chunk of it |
| What a bare "batch complete" log shows | Nothing - or a debug line nobody reads in production | Nothing distinct - it looks identical to a real duplicate being correctly skipped | Nothing, or a caught exception with no record of which document it was |
| How to confirm | Re-run extraction on that exact document by hand outside the batch | Pull up both documents and read them - is the match real | Check whether the document's id exists in the index at all |
| Where the fix goes | The parser's error handling: log the failure with the document id, and retry transient ones the way *Retries and fallbacks* retries a model call | The similarity threshold or the canonical-source logic in *One document, five copies* | Retry transient failures with backoff; for a genuine rejection, fail that document loudly instead of swallowing it |

The middle row is worth sitting with. A dedup false positive doesn't look like a failure in the log at all - it looks exactly like the system correctly doing its job, because from the pipeline's point of view, dropping a duplicate is success. The only way to tell "correctly skipped, it really was a duplicate" apart from "wrongly skipped, it was not" is to have kept enough of a record - which document was matched against which - that you can go check.

The same discipline from *Retries and fallbacks* applies directly to the third row: a 429 from your embedding provider or a transient write error is worth a retry with backoff; a document that's rejected outright - too large, wrong encoding, genuinely malformed - is not, and belongs in a place a human will see it rather than in a silently incremented failure counter nobody reads.

## 3. Log this from the start, or you are guessing

None of the above works from a summary log line written after the fact. It has to be one record per document per stage, written as the pipeline runs, because a batch job you re-run to "see what happens" usually processes a different subset of failures the second time - which feels like new information and is actually just noise.

```python
from dataclasses import dataclass
from enum import Enum

class Stage(Enum):
    EXTRACT = "extract"
    DEDUP = "dedup"
    CHUNK = "chunk"
    EMBED = "embed"
    WRITE = "write"

@dataclass
class IngestionRecord:
    batch_id: str
    doc_id: str
    stage: Stage
    ok: bool
    reason: str | None = None   # why it failed, verbatim - never a summary

def batch_reconciled(records: list[IngestionRecord], attempted: int) -> bool:
    """A batch is successful only if every attempted document has an ok
    record at the final stage - never just because the loop didn't crash."""
    landed = {r.doc_id for r in records if r.stage is Stage.WRITE and r.ok}
    return len(landed) == attempted
```

`batch_reconciled` is the fix to section one's whole problem: it makes "success" mean what you actually want it to mean, by checking the thing that matters - documents attempted versus documents that reached the last stage - instead of trusting the loop's own exit code.

Three fields make this record worth keeping at all: `batch_id`, so you can pull one run's documents out of everything else you've logged; `doc_id` and `stage`, so you know exactly which document stalled and where; and `reason`, the verbatim error, not a category you invented afterward - a category hides the detail that would have told you it was a dedup false positive rather than a parse failure. Write one of these per document per stage it passes through or fails at, and reconciliation stops being a question you have to investigate and becomes a query you run every morning.
